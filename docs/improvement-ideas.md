instead of a bare `str`. `AnthropicLLM`, `KiloLLM`, and `OpenRouterLLM` pass a

## 3. Security & safety

- ***~~Approval callbacks aren't authenticated.~~** — **DONE (2026-07-29)**: `ApprovalGate` now binds each pending approval to the requesting `chat_id` (`core/safety.py`: `_pending` stores `(chat_id, event)` tuples). `resolve()` requires the caller's `chat_id` and rejects the resolution if it does not match the approval's owner, closing the forwarded-message / guessed-id vector. It also no longer writes to `_results` for unknown or expired approval ids, fixing the set-before-registered race. `interfaces/telegram.py` `_on_callback` extracts the callback's `effective_chat.id`, passes it to `resolve()`, and shows an opaque "not valid or expired" message when rejected so an attacker cannot distinguish unknown from wrong-chat approvals.
- ***~~HTTP auth = one shared code, unlimited tokens.~~** — **DONE (2026-07-29)**: added `MAX_HTTP_SESSIONS` (default 10) cap so a leaked pairing code cannot mint sessions forever, and `HTTP_PAIR_RATE_LIMIT_RPM` (default 10/min/IP) on `POST /pair` to slow brute-force/minting. Admin endpoints now provide token revocation beyond self-delete: `GET /admin/sessions` lists active sessions with masked token prefixes, `DELETE /admin/sessions/{token}` revokes a specific session, and `DELETE /admin/sessions` revokes all sessions. All require the pairing code and write through to `StateStore`.
- ***~~Agent creator executes unvalidated LLM-generated Python.~~** — **DONE (2026-07-29)**: `/newagent` no longer writes LLM output straight to disk. `core/agent_creator.py` now does, in order: `_validate_generated()` runs `ast.parse()` on `agent_py` (and on `tools_stub` when `has_tools`) to catch syntax errors without executing, shape-checks required string fields, enforces `agent.module_name` matches the wizard-chosen name, and rejects skill filenames that aren't lowercase `*.md` basenames (no path separators/dirs) — killing the `../`/absolute-path traversal vector. `_write_agent_files()` keeps an independent basename + regex guard so a bypassed validator still can't escape `skills/`. The wizard gained a `confirm` step: after successful validation it parks the session (`WizardSession.generated`), shows a **preview** (file list + counts + a truncated `agent.py`, capped at 60 lines / 2000 chars) and asks the user to reply `yes`/`y`/`ok`/`confirm` (write) or `no`/`n`/`cancel` (discard, nothing on disk). Refuses anything else at that step. A *real diff* was intentionally not used since generated files are all new (name conflicts rejected up front), so a unified diff would be the whole file marked `+++`; the preview is the honest equivalent.
- ***~~No way to clear a pairing lockout.~~** — **DONE (2026-07-19, 2026-07-30)**: `PairingManager.MAX_FAILED_ATTEMPTS` (5) locked a chat_id permanently once persistence landed (§1.4) — `is_locked()` now survives restarts, and `delete_failed_attempts()` is only ever called from the success branch of `try_pair()`, which is unreachable once locked (`core/safety.py`). Added `PairingManager.unlock()` method and `POST /admin/unlock` endpoint (HTTP) to clear lockouts. Telegram interface now also has an `/unlock <chat_id>` command (`interfaces/telegram.py`), restricted to pre-allowed admin chat IDs.
- ***~~Rate limiter uses wall-clock time.time()~~** — **DONE (2026-07-19)**: `RateLimiter.is_allowed()`/`wait_time()` now use `time.monotonic()` (`core/safety.py`), immune to NTP jumps/clock changes mid-window.
- ***~~Unencrypted DB is silent~~** — **DONE (2026-07-19)**: `main.py`'s `bootstrap()` now logs a warning at startup when `DB_ENCRYPTION_KEY` is unset. Log-only, not fatal in any environment — a visibility fix, not policy enforcement.
- ***~~systemd hardening absent~~** — **DONE (2026-07-19)**: `StartLimitInterval`/`StartLimitBurst` moved to `[Unit]`; added `NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`, a scoped `ReadWritePaths` for the app's `memory/` dir, and `MemoryMax=512M` (`modular-agents.service`). `setup.sh`'s human-user install is unchanged — a dedicated-user install is a separate, larger operational change, explicitly out of scope for this pass.
- ~~**Pairing code comparison is not constant-time.**~~ — **DONE (2026-07-30)**: Added `PairingManager.verify_code()` (`core/safety.py`) using `secrets.compare_digest` after `strip().lower()` normalization; `try_pair()` now routes through it. Updated `interfaces/http.py` `/pair` and all admin endpoints to use `verify_code()` instead of `!=` / `==`. This closes the timing side-channel for both Telegram and HTTP pairing-code checks.

## 4. Reliability & error handling

- **~~Notifier failures are invisible to callers.~~** — **DONE (2026-07-28)**: `core/protocols.py` now defines `NotificationError` and the `Notifier` protocol documents that delivery methods raise on failure. `core/notifier.py` `_send_with_retry()` retries on Telegram `RetryAfter` with backoff and raises `NotificationError` for unrecoverable errors or excessive flood waits. `TelegramNotifier.send`/`send_media`/`send_with_buttons`/`send_and_get_id`/`delete_message` now raise instead of swallowing. `ApprovalGate.request_approval()` (`core/safety.py`) catches delivery failures, returns `False` immediately, cleans up the orphan event, and attempts a plain-text fallback so the user sees the failure instead of a silent timeout-deny.
- **~~Railway health parsing → hourly alert spam.~~** — **DONE (2026-07-28)**:  `healthy` requires status ∈ `("ACTIVE","SUCCESS","DEPLOYED")` parsed by substring-matching free-text CLI output (`railway.py:292, 301-317`). If the CLI output format shifts, the hourly `incident_watchdog` fires forever. `--json` is not available for the wrapped commands, so free-text parsing remains the only path; test the parsers against CLI output changes.
- **~~`telegram_allowed_chat_ids[0]` as the universal scheduled-message target~~** — **DONE (2026-07-28)**: — empty list → `chat_id=""` and scheduled sends silently vanish. Every agent copy-pastes this landmine (business `agent.py:310`, devops `:455`, wellbeing, librarian, projects). Fix once in `BaseAgent` (see 7.1).
- **~~Storage opens a fresh connection (and re-derives the SQLCipher key) on every query~~** — **DONE (2026-07-28)**: `Storage` now keeps a single long-lived `aiosqlite.Connection` opened during `init()` and reused for every query (`core/storage.py`). The SQLCipher key is applied once at connection setup, and `PRAGMA busy_timeout = 5000` avoids transient lock contention with `StateStore`'s per-query connections. `get_or_create_session` uses `INSERT OR IGNORE` to close the old check-then-insert race. `Storage.close()` is called from `main.py`'s shutdown `finally` block.
- **~~Timezones are inconsistent~~** — **DONE (2026-07-28)**: Added `USER_TIMEZONE` setting (`core/config.py`) defaulting to UTC. `core/timezone.py` provides `load_timezone()`, `now_in_user_timezone()`, and `as_user_timezone()`. `core/quiet_hours.py` now evaluates windows in the user's timezone; `core/scheduler.py` passes the timezone to `CronTrigger.from_crontab()` so cron jobs fire in the same zone. `main.py` calls `_scheduler.set_timezone(settings.user_timezone)` at startup. `agents/wellbeing/agent.py` also uses the user timezone for "already sent today" checks and date-based state so scheduled nudges and internal state agree. 
- **~~Logger config is an ordering trap.~~** — **DONE (2026-07-28)**: `get_logger` lazily configured with defaults, and if any module logged before `main.py` called `configure_logging`, real settings became a silent no-op (`core/logger.py:153-155`). `configure_logging()` now passes `force=True` (clearing `root.handlers` first) so it always applies as authoritative, even after an earlier lazy default `_configure()`. Redaction now covers any field in `_REDACTED_FIELD_NAMES` (`{"content", "text"}`) instead of only the literal `content`; covered by `tests/test_logger_config.py`.

## 6. Interfaces & UX

- **~~CLI can't target agents~~** — **DONE** (already fixed, found stale 2026-07-25): `core/routing.py`'s `parse_agent_tag()` is already wired into all three interfaces — `interfaces/cli.py:57`, `interfaces/telegram.py:133`, `interfaces/http.py:197` — evidently landed alongside item 1.3's routing work; this entry just never got updated. - **~~Pairing/rate-limit logic is triplicated~~** — **DONE (2026-07-25)**: pairing turned out to be three intentionally different models (Telegram: conversational, tracks attempts remaining; HTTP: token-exchange via `POST /pair`; CLI: auto-paired as trusted) — not unified, since collapsing them would lose real UX differences. What *was* genuinely duplicated: rate-limit check logic (`is_allowed()` + `wait_time()` + message formatting), now `RateLimiter.check()` (`core/safety.py`) used by both `telegram.py` and `http.py`. Also deduped Telegram's own internal "not paired" guard — it was repeated 3x across `_on_model`/`_on_planmode`/`_on_command` with two different messages/delivery paths — into one `TelegramInterface._require_paired()` helper, standardized on the more informative "send the pairing token" message via `bus.send_notification`.
- **~~/model mutates the global default for everyone~~** — **DONE (2026-07-25, 2026-07-30)**: scoped per-chat rather than per-agent — per-agent runtime overrides would have duplicated the `<AGENT>_AGENT_MODEL` env vars item 2.3 already shipped. New `chat_model_map` table (`core/state_store.py`), `MessageBus.get_chat_model()`/`set_chat_model()`/`clear_chat_model()` (mirrors the `chat_agent_map` persistence pattern), and `BaseAgent.resolve_model(chat_id)` giving precedence: chat override → agent's env var → global default. `/model` in `telegram.py` now calls `bus.set_chat_model()` instead of mutating `settings.default_model`; added `/model reset` to clear the override. HTTP interface now has matching endpoints (`GET /model`, `POST /model`, `DELETE /model`) tied to the session's `chat_id` (`interfaces/http.py`).
- **~~Duplicate _on_message registration in groups 0 and 1~~** — **DONE (2026-07-19)**: confirmed as a live bug, not just a smell — python-telegram-bot evaluates handler groups independently, so every private-chat text message was processed twice (double rate-limit consumption, double agent dispatch, two replies per message). Removed the redundant group=1 registration; handler registration extracted into `_register_handlers()` for testability (`interfaces/telegram.py`, `tests/test_telegram_handler_registration.py`).
- **~~Telegram reaches into pairing._failed_attempts~~** — **DONE (2026-07-19)**: added `PairingManager.attempts_remaining()` (`core/safety.py`), `interfaces/telegram.py` now calls it instead of the private attr. Also fixed a stale message found alongside it: the locked-chat reply said "Restart the bot to try again" — no longer true since §1.4's lockout persistence; now points to the administrator instead.
- **~~No HTTP streaming/SSE~~ and the ~~notifier.get_and_clear() out-of-band capture~~** (`http.py:139-148`) race condition — **DONE (2026-07-25)**: added `POST /message/stream` SSE endpoint to `interfaces/http.py` that streams agent responses in real-time as notifications arrive. Fixed the race condition by adding per-chat_id asyncio.Queue and per-chat_id Lock to `HTTPNotifier` (`core/notifier.py`) — notifications are now streamed via the queue while the agent processes, and `get_and_clear()` is protected by the lock for concurrent requests. `notify_done()` signals stream completion; `stream_queue()` helper yields events for SSE consumption. Added to `RouterNotifier` for proper dispatch.
- **~~Echo agent is still registered in production~~** — **DONE (2026-07-19)**: added `DEBUG_ECHO_AGENT` (`core/config.py`, default `false`) — `main.py` only constructs/registers `EchoAgent` when set. Before this, `routable=False` only excluded it from the LLM content-classifier's candidate pool; it was still reachable via explicit `@echo` tagging (`bus.registered_agents` included it unconditionally) and even via classifier hallucination, since `_resolve_agent()` only checks `picked in self._agents`, not membership in the offered candidate set.
- **~~No "which agent am I talking to?" indicator~~** — **DONE (2026-07-25)**: routing turned out to be even less predictable than "sticky" implies — `bus._resolve_agent()` runs explicit `@tag` → LLM content-classifier (can silently switch agents based on message content alone) → sticky last-agent → first-registered, so the active agent can change without the user doing anything. `BaseAgent.reply()` (`agents/base.py`) — the single choke point every agent's conversational response passes through — now prefixes the delivered text with `[{agent_name}]`. `AgentResponse.text` itself (used for memory and HTTP's JSON) stays unprefixed; HTTP already returns a separate structured `"agent"` field, which is the more appropriate indicator for an API consumer than a text prefix.
- **HTTP interface security and functional gaps — unreported bugs (2026-07-30).** Investigation of `interfaces/http.py` and its supporting `core/notifier.py` / `core/safety.py` paths found issues beyond the items already closed in §3 and §6. Current tests cover session persistence, admin endpoints, rate-limit caps, and tag parsing; the message/SSE paths and pairing-comparison paths are untested.
  - ~~**Critical**: `/pair` and admin endpoints compare the pairing code with non-constant-time `!=` / `==` (also see §3). Brute-force can be accelerated by timing.~~ — **DONE (2026-07-30)**: `PairingManager.verify_code()` now uses `secrets.compare_digest`; HTTP `/pair` and admin endpoints route through it.
  - ~~**Critical**: `/pair` invokes the per-IP rate limiter *after* validating the code. Wrong-code requests return 403 before the limiter is touched, so the rate limit does not slow brute-force attempts.~~ — **DONE (2026-07-30)**: `/pair` now checks the per-IP rate limiter before validating the pairing code, so wrong-code brute-force attempts consume the bucket.
  - **High**: `/pair` calls `PairingManager.pair_directly()`, which bypasses `is_locked()` and failed-attempt counting. A chat_id locked out on Telegram can still obtain an HTTP session if it knows the code.
  - **High**: HTTP has no approval/callback path. `HTTPNotifier.send_with_buttons()` silently drops button payloads and sends only text, so supervised agents requiring approval cannot be approved over HTTP.
  - **Medium**: `/message/stream` loses the agent name and `success` flag. `notify_done()` only receives `response.text`; the final SSE event hardcodes `"agent": ""` and `"success": True`.
  - **Medium**: `HTTPNotifier.get_and_clear()` claims to be lock-protected but never acquires the per-chat `asyncio.Lock`. Concurrent `/message` requests for the same chat_id can race on `self._buffers.pop(chat_id, [])`.
  - **Medium**: `HTTPNotifier` per-chat buffers, queues, and locks are never evicted. Long-running processes with many sessions leak memory.
  - **Medium**: The creator path in `/message` returns without calling `get_and_clear()`, so creator progress notifications can leak into the next `/message` response for that chat_id.
  - **Low**: `HTTPNotifier.stream_queue()` is defined and forwarded through `RouterNotifier`, but `/message/stream` reads the queue directly via `_get_queue()`. Dead code.
  - **Low**: Per-IP rate limiting uses `request.client.host`, which is usually `127.0.0.1` behind a reverse proxy, so all clients share one bucket. Should honor `X-Forwarded-For` when configured.
  - **Low**: `/message` uses `response.text or extra or ""`, so an agent that intentionally returns empty text has its response overridden by buffered extras.
  - **Low**: Admin endpoints have no rate limiting beyond the pairing code; a leaked code enables rapid enumeration/revocation.
  - **Low**: No tests exercise `/message` or `/message/stream` end-to-end behavior (only tag parsing in `test_interface_routing.py`).

## 7. Code architecture & hygiene

- **~~Declarative schedules in `BaseAgent`.~~** — **DONE (2026-07-24)**...

- **WellbeingAgent schedule, state, and skill drift — unreported bugs (2026-07-30).** Investigation of `agents/wellbeing/agent.py` found several issues not previously tracked. Tests pass because they mock `_load_state`, `_save_state`, and `_get_weather`, so these are runtime-only:
  1. **Cron schedules in code do not match docstring or skill files.** `SCHEDULES` has weekday at 06:00 (docstring/skills say 07:00), weekend at 07:00 (docstring/skills say 08:00), follow-up at 08:00 (skills say 08:30), and evening at 20:30 (skills say 19:30). Bedtime and weekly match.
  2. **Weekly check-in uses a partial-week denominator instead of 7 days.** `_do_weekly()` computes `total_days = min(7, (today - monday).days + 1)` and uses it in both the message (`N/total_days days`) and the percentage thresholds. The skill specifies a 7-day denominator for both. On Monday this reports `1/1 days` and triggers “Strong week.”
  3. **Morning follow-up fires regardless of whether the user replied.** `_do_followup()` only checks `_already_sent_today`; it never inspects storage for a reply to the morning nudge. The skill says to skip the follow-up when the user already replied.
  4. **Morning message ignores the skill’s message pool.** `morning-nudge.md` defines three weekday messages, three weekend messages, and two weather fallbacks. The agent hardcodes a single message template per case.
  5. **Skill files are completely unused.** Since `_load_skill` was removed, none of the five `agents/wellbeing/skills/*.md` files are read. Skill-defined deflection rules (medical topics, complex emotional support, exact “send now” wording) are ignored.
  6. **Blocking I/O inside async handlers.** `_get_weather()` calls `subprocess.run()` directly (up to 10 s block), and `_load_state()` / `_save_state()` do synchronous `Path` I/O inside async scheduled handlers.
  7. **`_send_to_all_chats()` broadcasts to every allowed chat.** Scheduled events carry `chat_id = telegram_allowed_chat_ids[0]`, but the handler ignores it and loops over all configured chat IDs. Probably intentional broadcast, but inconsistent with interactive replies.
  8. **`_pick_message()` is dead code.** Uses `random.choice()`, but evening/bedtime use `_pick_cyclic()` and morning uses `_build_morning_message()`.
  9. **`wellbeing_wake_time` / `wellbeing_bedtime` settings are unused.** Parsed by `core/config.py` but never read by the agent.
  10. **`_respond_settings()` falsely claims it can update preferences.** Tells the user *“…or tell me what you need and I can update it there”* with no code path that writes to `memory/context/preferences.md`.
